## 1. Feedback、Sense–Think–Act–Evolve 与 Open Loop

Robotics system 最基本的思考方式之一，是一个不断重复的 feedback loop。

Lecture 把它概括成：

```text
Sense
  ↓
Think
  ↓
Act
  ↓
Evolve
  ↓
Sense again
```

**Sense** 是获取系统当前最新的信息，也就是通过 sensors 得到 observation。

**Think** 是根据当前 information，使用 decision algorithm / control policy 决定接下来应该做什么。

**Act** 是把 decision 转成实际 command，例如 speed command、steering command、orientation command。

**Evolve** 表示系统在这个 command 下运行一段时间，进入新的 state，然后重新进行 sensing。

所以 feedback control 的关键不是“有一个 controller”，而是：

\[
\boxed{
\text{new state}
\rightarrow
\text{new measurement}
\rightarrow
\text{new decision}
}
\]

也就是说，系统会根据实际发生的结果不断修改后续行为。

如果我们把这个 feedback connection 切断，只在最开始 sense 一次、plan 一次，然后完全按照原始 plan 执行，就变成 **open-loop control**。

```text
Initial information
      ↓
Plan once
      ↓
Execute entire plan
```

Open loop 最大的问题是：如果 environment 或 system 本身发生变化，原来的 plan 可能已经不适用了，但系统不会知道。

不过 open loop 并不是“错误的”。它在某些场景很合理，例如 **system identification / experiment design**。

如果你的目标不是实时控制，而是故意给系统一串 predefined inputs，然后观察 response，用来估计 model parameters，那么你反而不希望 collected measurements 中途改变 experiment。

因此：

> Closed loop 的目标通常是根据新 information 修正行为；open loop 在某些 experiment / system identification 问题中反而更合适。

## 2. Robotics Design Process：从 Requirement 到 Policy

Lecture 给出的是一个工程化的 design process，而不是一条“唯一正确”的规则。

核心流程可以理解成：

```text
1. Define requirements
        ↓
2. Build / choose a model
        ↓
3. Select inputs, outputs, sensors, actions
        ↓
4. Design a policy
        ↓
5. Evaluate performance
        ↓
6. Iterate
```

重点在于 **iteration**。

实际设计很少第一次就完成。你可能设计完 policy 后才发现 sensor information 不够；也可能发现 requirement 本身无法保证；或者发现 model 太简单，无法解释 observed behavior。

因此这些步骤不是只能单向进行，而是会不断来回调整。

Lecture 还提到 block diagram 的作用。

Block diagram 的优点是可以用较高层次描述 system components 以及信息如何流动，避免陷入 implementation detail。

但 limitation 是它容易隐藏 **time**，同时如果 abstraction level 选错，也可能变得和原系统一样复杂。

因此真正困难的不是“会不会画 block diagram”，而是：

\[
\boxed{
\text{选择合适的 abstraction level}
}
\]

画太少没有信息，画太多又失去了 block diagram 的意义。

## 3. Requirements：把自然语言变成可量化指标

用户或 client 提出的 requirement 往往是模糊的，例如：

- respect the speed limit
- drive smoothly
- stay close to the centre of the lane

人类大概知道这些是什么意思，但对于 engineering system 来说不够 precise。

例如：

> “Respect the speed limit”

至少可以有不同 interpretation。

可以定义“超过 speed limit 超过 1 km/h 的累计时间”：

\[
J_1
=
\sum_k
\mathbf{1}
\left[
v_k > v_{\text{limit}}+1
\right]
\]

也可以定义最大超速程度：

\[
J_2
=
\max_k
\left(v_k-v_{\text{limit}}\right)
\]

这两个 metrics 都是在描述“respect speed limit”，但它们对应完全不同的行为。

一个 policy 可能偶尔严重超速一次，但大部分时间正常；另一个 policy 可能只轻微超速，但持续很久。哪个更好，取决于你的 requirement 到底想表达什么。

这就是为什么 lecture 强调 mathematics 的作用是 **precision**。

Natural language 可以保留 vagueness，但 equation 会迫使 designer 明确：

\[
\boxed{
\text{到底什么叫“good performance”？}
}
\]

类似地，“smooth driving”可以通过 acceleration change、jerk 或 control variation 来描述。

例如简单地限制：

\[
|a_{k+1}-a_k|
\]

不能太大。

因此 requirements engineering 的关键不是把一句话翻译成唯一公式，而是：

> 先识别你真正关心的 performance property，再选择能够量化它的 metric。

## 4. Models：Fidelity、Kinematic 与 Dynamic Model

Model 是我们对真实 system behavior 的 mathematical approximation。

同一个 physical system 可以有很多不同 fidelity 的 model。

以 lecture 中抛球为例。

最简单可以只考虑基本 motion：

\[
F=ma
\]

进一步可以加入：

- air drag
- wind
- pressure
- temperature
- 更复杂的 aerodynamic effects

理论上甚至可以一直增加 detail，但更 detailed 并不等于更 useful。

这是一个非常重要的 engineering trade-off：

```text
Low-fidelity model
→ simple
→ fast simulation
→ easy analysis
→ less realistic

High-fidelity model
→ more realistic
→ more computation
→ slower simulation
→ harder analysis
```

所以 model fidelity 应该由 **task** 决定。

如果一个简单 model 已经足够帮助你设计 controller，就没有必要一开始构造极其复杂的 simulator。

Lecture 还区分了 **kinematic model** 和 **dynamic model**。

Kinematic model 更关注：

\[
\text{position}
\leftrightarrow
\text{velocity}
\]

例如：

\[
\dot{x}=v
\]

它描述 motion geometry，但不解释 force 是如何产生 velocity 的。

Dynamic model 则会包含 force、mass、torque、voltage 等：

\[
m\dot{v}=F
\]

因此 dynamic model 更接近 physical actuation，但也更复杂。

对于 car，真实车辆有四个 wheels、suspension、weight transfer、tire forces 等。

为了设计方便，常常会进行 simplification，例如把左右两个 front wheels 合并成一个 front wheel，两个 rear wheels 合并成一个 rear wheel，得到常见的 **bicycle model**。

这反映了整节课一直强调的原则：

\[
\boxed{
\text{Start simple, add complexity only when needed}
}
\]

## 5. Sensors、State 与 Observability

Robot 的真实 internal state 通常不能被 controller 直接读取。

现实中我们拿到的是 sensor measurements：

\[
y_t
=
h(x_t)
+
\text{noise}
\]

其中：

- \(x_t\)：真实 state
- \(y_t\)：measurement / observation
- \(h(\cdot)\)：measurement model

这是 lecture 中很重要的一点：

> **state 不等于 observation。**

Simulation 中有时可以直接读取 simulator 的 ground-truth state，但真实 robot 通常没有这种“作弊能力”。

因此设计 sensor system 时，要问一个更根本的问题：

\[
\boxed{
\text{这些 measurements 是否包含足够 information 来推断我们需要的 state？}
}
\]

这就是 **observability**。

如果系统内部 state 能够通过一段时间的 observations 被推断出来，那么这个 system 在该 measurement setup 下是 observable。

Lecture 用“只测 velocity，能不能知道 position”来解释。

如果只知道当前 velocity：

\[
v(t)
\]

但完全不知道 initial position：

\[
x(0)
\]

那么很多不同 position trajectories 都可以产生相同 velocity measurements。

因为：

\[
x(t)
=
x(0)
+
\int_0^t v(\tau)d\tau
\]

如果 \(x(0)\) 不知道，position 就不能唯一确定。

因此仅有 velocity measurement 时，absolute position 可能是 **unobservable**。

另一个例子是 angular position。

如果 model 已知，并且连续测量 angle：

\[
\theta(t)
\]

那么通常可以从 time evolution 中推断 angular velocity：

\[
\dot{\theta}(t)
\]

因此 angle + system dynamics 可能足以 infer angular velocity。

Observability 不只是“sensor 多不多”，而是：

> sensor measurements 和 system dynamics 结合之后，能不能 distinguish different internal states。

同时还要区分：

1. **理论上能不能估计**
2. **实际上估计得准不准**

即使 system observable，sensor noise 仍然可能让 estimate 很差。

例如 velocity measurement 有 noise，而你不断积分估算 position：

\[
\hat{x}(t)
=
x_0+\int_0^t \hat{v}(\tau)d\tau
\]

noise 会逐渐 accumulation，因此 uncertainty 可能随着时间增长。

如果偶尔得到 absolute position measurement，就可以重新修正 accumulated error。

所以 observability 是一个 fundamental feasibility question：

\[
\boxed{
\text{如果 measurement 根本不包含 state information，任何 policy 都无法补救。}
}
\]

## 6. Policy Evaluation 与 Pareto Frontier

设计完 policy 后不能只跑一次 simulation 然后说“works”。

Robot 在 deployment 时会面对不同：

- initial conditions
- model parameters
- disturbances
- sensor noise
- environment conditions

因此 policy evaluation 应该在一系列 scenarios 上进行。

可以把它理解成：

```text
Choose policy
     ↓
Vary parameters / initial states / noise
     ↓
Run many simulations
     ↓
Collect performance metrics
     ↓
Assess robustness
```

这本质上是在问：

> 在不同可能 operating conditions 下，我有多大 confidence 这个 policy 仍然满足 requirements？

这和 safety 也直接相关。

我们关心的不只是 average performance，而是 catastrophic failure 是否可能发生。

另一个重要问题是：通常我们不只有一个 performance metric。

例如：

- cost
- accuracy
- energy use
- time
- comfort
- safety margin

一个 policy 很可能在某个 metric 上更好，却在另一个 metric 上更差。

这就是 multi-objective trade-off。

Lecture 用 **Pareto frontier** 表示这种关系。

如果 policy A 在所有 metrics 上都不差于 policy B，并且至少一个 metric 更好，那么 A **dominates** B。

被 dominated 的 policies 一般没有继续考虑的价值。

Pareto frontier 上的 policy 则满足：

> 想改善一个 metric，就必须牺牲至少另一个 metric。

所以 frontier 上不存在“全面更好”的选择，只剩 engineering trade-off。

这比把所有 metrics 强行组合成一个 score 更有解释力，因为如果 metrics 一个是 dollars、一个是 seconds，你必须人为选择 exchange rate / weight。

Pareto view 可以避免过早决定这种 arbitrary weighting。

## 7. PID Controller：P、I、D 分别在做什么？

PID 是 lecture 中的一个典型 policy family，特别适合理解 policy synthesis。

对于 tracking problem，定义 error：

\[
e(t)=r(t)-y(t)
\]

其中：

- \(r(t)\)：reference
- \(y(t)\)：actual output

PID control law：

\[
u(t)
=
K_Pe(t)
+
K_I\int_0^t e(\tau)d\tau
+
K_D\frac{de(t)}{dt}
\]

可以用 lecture 里的方式记：

```text
P → present
I → past
D → future tendency
```

### Proportional term

\[
K_Pe(t)
\]

只看当前 error。

error 越大，corrective action 越大。

可以把 P 想象成一根 spring：离 reference 越远，拉回来的力量越强。

### Integral term

\[
K_I\int e(t)dt
\]

累积过去的 error。

如果 system 长时间有一个小但持续存在的 steady-state error，积分会不断积累，最终产生 correction。

因此 I 的主要作用之一是：

\[
\boxed{
\text{remove steady-state error}
}
\]

### Derivative term

\[
K_D\frac{de}{dt}
\]

看 error 正在多快变化。

如果 error 正在快速接近 reference，D 会提前产生 damping effect，减少 overshoot / oscillation。

因此 lecture 用“future tendency”帮助理解 D。

它并不是预测真正的未来，而是利用当前 derivative 判断 error trend。

经典 tuning intuition：

```text
1. Start with P
2. Increase P until response becomes aggressive / oscillatory
3. Add D to reduce oscillation
4. Add I to remove steady-state error
```

典型 performance measures 包括：

- rise time
- overshoot
- settling time
- steady-state error

PID 也有明显 limitation。

Derivative 对 noise 非常敏感，因为 differentiation 会放大 high-frequency noise。

Integral 则可能发生 **integral wind-up**：如果 actuator 已经 saturated，但 error 仍持续存在，integral term 会继续积累，导致之后出现很大的 unwanted control action。

另外 PID 天然最容易用于 SISO：

\[
\text{single input}
\rightarrow
\text{single output}
\]

如果多个 loops 强烈 coupled，多个独立 PID controllers 可能互相“打架”。

例如 car 中 steering 和 speed 并不是完全 independent：高速下微小 steering change 对 lateral motion 的影响会更大。

## 8. Reward Engineering：你写的 Objective 就是你真正要求系统做的事

无论 reinforcement learning 还是 MPC，都经常需要定义 reward / cost / objective。

最关键的问题不是“optimizer 强不强”，而是：

\[
\boxed{
\text{你写下的 objective 是否真的代表你想要的 behavior？}
}
\]

如果 reward 设计错了，agent 可能非常成功地优化了一个错误目标。

Lecture 给出的直观例子：

> “Minimize robot energy consumption.”

如果没有其他 requirement，那么最优 solution 可能就是：

\[
\boxed{
\text{Robot does nothing}
}
\]

这不是 optimizer 出错，而是它准确完成了你给它的 objective。

因此：

\[
\text{Desired behavior}
\neq
\text{Poorly specified reward}
\]

reward engineering 就是建立这两者之间的 correspondence。

Reward 设计的一个原则是尽量从 system physics 和真正的 performance requirement 出发，例如：

- energy
- distance
- tracking error
- money
- time
- safety violation

如果 performance 很抽象，也可能需要 learning from demonstrations / inverse optimal control 等方法去推断人类真正偏好的 objective。

另一个原则是不要一开始就设计非常复杂的 reward。

先用少量 components：

\[
R
=
R_1 + R_2
\]

理解 behavior 后再逐渐加入：

\[
R
=
w_1R_1+w_2R_2+w_3R_3+\cdots
\]

但每增加一个 term，就可能引入新的 trade-off 或 unintended consequence，因此必须 stress-test。

Lecture 还指出，在 MPC 中 objective 不仅仅决定“performance 好不好”，有时还和 system stability、constraint satisfaction 有关。

因此 reward / cost 并不是一个可随便调整的 score，而是整个 policy behavior 的 mathematical specification。

## 9. Exam / Revision Cheat Sheet

**Feedback loop**

```text
Sense → Think → Act → Evolve → Sense ...
```

Closed loop 会根据新 measurements 修正 decision。

**Open loop**

只根据 initial information 规划，之后不根据新 state 修改 plan。

适用于某些 experiment design / system identification。

---

**Design process**

```text
Requirements
→ Model
→ Sensors / Actions
→ Policy
→ Evaluation
→ Iterate
```

---

**Requirement engineering**

Natural language 通常 vague。

需要把：

```text
"drive smoothly"
"stay close to lane centre"
"respect speed limit"
```

转成 precise performance metrics。

---

**Model fidelity**

```text
Low fidelity
= simple + fast + less realistic

High fidelity
= detailed + slow + more realistic
```

不是 fidelity 越高越好，要看 task。

---

**Kinematic vs Dynamic**

\[
\dot{x}=v
\]

是 kinematic relation。

\[
m\dot{v}=F
\]

加入 force / mass 后属于 dynamic model。

---

**State vs Observation**

\[
x_t = \text{internal state}
\]

\[
y_t = \text{sensor measurement}
\]

现实中 controller 通常只能直接得到 \(y_t\)，不是 \(x_t\)。

---

**Observability**

核心问题：

\[
\boxed{
\text{Can observations uniquely reveal the required state?}
}
\]

如果不能，policy 再强也无法解决。

---

**Policy evaluation**

不要只跑一个 scenario。

要 variation：

```text
initial state
parameters
noise
disturbances
environment
```

然后分析 performance distribution。

---

**Pareto frontier**

如果没有其他 policy 能在所有 metrics 上至少一样好、并在一个 metric 上更好，那么该 policy 是 non-dominated。

Pareto frontier 上：

\[
\text{Improve one objective}
\Rightarrow
\text{worsen another}
\]

---

**PID**

\[
u(t)
=
K_Pe(t)
+
K_I\int e(t)dt
+
K_D\frac{de}{dt}
\]

记忆：

```text
P = Present error
I = Past accumulated error
D = Error trend / damping
```

P：当前 correction  
I：消除 steady-state error  
D：减少 overshoot / oscillation，但对 noise 敏感

---

**Typical control response metrics**

```text
Rise time
Overshoot
Settling time
Steady-state error
```

---

**Integral wind-up**

Actuator saturated 时，integral 仍不断累积，可能导致 excessive future control action。

---

**Reward engineering**

Agent 优化的是：

\[
\text{what you mathematically specify}
\]

不一定是：

\[
\text{what you intended}
\]

所以 reward 必须和 desired behavior 对齐。
